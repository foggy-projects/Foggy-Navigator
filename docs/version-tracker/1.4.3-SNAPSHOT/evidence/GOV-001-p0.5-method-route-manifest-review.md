## Security Review Decisions

### Risk tier and credential lane are independent dimensions

`risk_tier` describes the impact of the endpoint; `target_accepted_principal_lanes` describes which authenticated authority may perform it. They must not be derived from each other.

- All 244 non-GET MVC entries are at least R2.
- R3 includes destructive/security-boundary actions, but also high-impact business mutations whose correct caller remains an exact Navigator user, ClientApp control, runtime/task principal, share capability, or Worker principal.
- Only 32 rows require typed `SECURITY_ACTION`. The remaining 102 R3 rows intentionally do not become root/platform security actions merely because they are high risk.
- Conversely, a management security credential never authorizes `/api/v1/open/**` runtime ask/task/session calls; S1 instance-root authority cannot impersonate a runtime caller.

This separation prevents both under-classification and accidental privilege amplification.

### Sensitive session configuration read

`GET /api/v1/sessions/configs` is R2, not a normal R1 list. It returns sensitive authentication/configuration metadata such as auth binding, base URL, model configuration reference and masked token state. Its target contract requires exact Navigator-user tenant/session-config ownership resolution.

### ClientApp bootstrap credential

`POST /api/v1/admin/client-apps/provisioning-credentials` represents a one-time ClientApp bootstrap credential. It may be initiated by the existing tenant-admin flow and, in the target architecture, by `INSTANCE_ROOT/CONTROL_ACCESS` or `SAAS_PLATFORM/CONTROL_ACCESS(SAAS_PROVISIONING)` within exact instance/upstream/tenant authority.

It is not the API for issuing, rotating, revoking or recovering typed management-principal credentials; those operations remain separately registered security actions.

### Deployment-aware route identity

Overlapping paths in the launcher and Observer BFF have distinct route identities. For example:

- launcher: `mvc:post:/api/v1/open/agents/{agentId}/ask`
- Observer BFF: `mvc:observer-bff:post:/api/v1/open/agents/{agentId}/ask`

The `deployment` column is mandatory so route review, policy registration and audit cannot merge two different ingress/trust boundaries by path alone.

## Observer BFF Finding

The 12 routes under `tools/navigator-chat-observer-bff` are a separate deployment surface and are all marked:

- `surface=OBSERVER_BFF_LOCAL_TOOL`
- `disposition=LOCAL_TOOL_RESTRICT`
- `migration_mode=LOCAL_TOOL_AUTH_SESSION_AND_NETWORK_HARDENING`

Current source facts:

1. `server.address` defaults to `0.0.0.0` and port `5181`.
2. The BFF has no inbound observer authentication/session gate.
3. Runtime routes reuse a server-held ClientApp/API/bearer credential or a login-derived runtime credential.
4. `/api/v1/observer/auth/login` accepts Navigator account material and replaces one process-global in-memory runtime credential.
5. Attachment upload/read has no observer-session or task-capability binding; read possession is only the opaque path.
6. BFF `/api/v1/open/**` ingress does not pass through Navigator launcher `ExternalSurfaceGateFilter`. `NAVIGATOR_EXTERNAL_ENABLED` only applies later to the BFF's downstream Navigator `/open` request.

Security conclusion: the Observer BFF may only be treated as a local/trusted development tool. It is production-blocked until at least observer-session authentication, exact runtime-principal binding, attachment capability binding, CSRF/origin protection and an explicit network policy are implemented and tested. Setting `NAVIGATOR_EXTERNAL_ENABLED=true` does not secure or production-enable this BFF.
