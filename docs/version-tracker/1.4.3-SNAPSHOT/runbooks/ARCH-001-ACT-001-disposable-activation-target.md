# ARCH-001-ACT-001 Disposable Activation Target Runbook

## Authority boundary

This runbook is a five-phase protocol. Finishing one phase grants no
authority for the next phase.

1. Ultra implementation delivers source, tests, templates, and sanitized
   evidence. It must stop at `READY_FOR_SIGNOFF`.
2. A separately authorized closed-provisioning session may build only an exact
   disposable MySQL schema, start an activation-disabled loopback Navigator,
   create synthetic runtime resources through production APIs, seal the
   server-generated identities, stop the whole target, and purge short-lived
   bootstrap bearer/password material. It must not call a model or lifecycle
   activation mutation.
3. A fresh independent activation signoff reviews the exact candidate and the
   sealed stopped target and may
   return only `AUTHORIZED_FOR_ONE_BOUNDED_CANARY` or `REJECTED`. It does not
   start the target or invoke a model.
4. A later execution session requires both an accepted signoff and a separate
   user instruction naming the exact runId/target/model/window and allowing at
   most one model submission.
5. Cleanup and credential purge are part of that one execution; no retained
   credential profile is evidence.

The repository default and this implementation package keep activation
`CLOSED`. GOV-001-P3 remains blocked. Local canary evidence is not production,
external-ingress, or dev-kvm promotion authority.

## Immutable safety rules

- Target class is exactly `ISOLATED_LOCAL_NON_FIXTURE`; provider evidence lane
  is exactly `REAL_CODEX_MODEL`.
- Never reuse Navigator 8112, a shared database, the current Docker project, or
  Worker ports 3031/3051/3053/3061/3151/3161.
- Never reuse `/home/sa/.codex-worker`, `/home/sa/.claude-worker`,
  `/home/navigator/.codex-worker`, or a repository Worker directory as the
  target Worker home.
- Only loopback listeners, a unique database name, a unique Compose project,
  a unique target root containing the runId, and exact PID files are accepted.
- Do not access `accounts/`, sibling repositories, TMS/SIM, real business data,
  or Task `20260730-0e01`.
- Provider credential, short-lived bootstrap credential, narrow runtime
  credential, Worker lifecycle credential, activation control token, Navigator
  runtime settings, and database credential remain separate files. All profiles
  are target-owned, gitignored, regular non-symlink files with mode `0600`.
- Never put credential values, the prompt body, or the model response into a
  command line, log, manifest, candidate evidence, or signoff record.
- The prompt is a fixed synthetic no-tool string. The manifest stores only its
  SHA-256. Business runtime context, additional directories, network access,
  web search, developer instructions, and existing Session IDs are forbidden.
- Any unknown ownership, stale observation, proof loss, identity drift,
  Worker unavailability, controller relaunch, or cleanup mismatch stops the
  run. There is no automatic recovery or second attempt.
- A fresh execution schema is created only from the candidate-bound tracked
  schema plan. Its current-schema baseline may be generated once during Ultra
  implementation from the candidate on isolated MySQL 8.0.44, then reviewed,
  checked in and digest-sealed. Runtime Hibernate `update/create`, a directory
  scan that auto-admits new SQL, rollback SQL, test fixtures, and direct
  application-row DML are forbidden.
- User, Physical Worker, and modelConfig IDs are server-generated by existing
  production APIs during closed provisioning and then sealed. A public or
  internal route that accepts caller-selected primary keys is not permitted.

## Implementation checks and closed provisioning

Implementation validation may exercise the schema-plan and provisioning client
against target-owned disposable loopback resources without calling a model.
It must keep both activation switches false, must never call registration or
proof endpoints, and must end with all target resources stopped and short-lived
bootstrap bearer/password material purged.

The separately authorized closed-provisioning sequence is:

1. Recompute candidate identity, allocate a new target root and run live
   `doctor` plus `cleanup-plan`; both are zero-write and all ports/resources are
   absent.
2. Verify the sealed forward schema plan against the candidate. Start only the
   exact `mysql:8.0.44` Compose project with restart policy `no`; prove exact
   version, loopback, empty/owned database, then apply the strict ordered plan.
   Reapply it and capture content-free counts/digests.
3. Start only the copied candidate Navigator with Hibernate `validate`, both
   activation switches false, external and Worker Gateway surfaces closed.
4. Through existing production auth APIs, register a random synthetic user in
   the synthetic tenant and authenticate it. Through existing Worker APIs,
   register the dedicated Physical Worker endpoint and capture its generated
   ID. Bind that ID into the dedicated Worker profile, start the Worker, and
   verify authenticated health/build/protocol/capabilities.
5. Through the authenticated production modelConfig API, create one restricted
   `OPENAI_CODEX` config whose only allowed Worker is the generated Physical
   Worker. Read provider material in-process from the separate provider profile;
   request bodies, bearer material and responses containing secrets must not be
   logged or placed in argv. Do not invoke connection-test or any model route.
6. Create the narrow runtime credential needed for the later one task, verify
   exact tenant/user/Worker/modelConfig grant and stopped-safe readiness, then
   delete the short-lived bootstrap bearer/password profile.
7. Stop the exact Worker, Navigator, and MySQL resources; write the generated
   IDs and content-free verification results into an atomic seal/final manifest.
   Run stopped-target `doctor` and `cleanup-plan` again with zero writes.

The independent reviewer then checks:

- candidate HEAD and dirty-tree digest match the evidence manifest;
- default Navigator and Worker activation switches are false;
- the production request surface contains no fixture/evidence/readiness/proof
  authority booleans;
- the internal control route accepts no request body and is protected by the
  exact target-owned control token, not JWT/admin/runtime credentials;
- controller inventory is the fixed six-kind contract and observations come
  from `LIVE_LOCAL_INSPECTION`, never an offline snapshot;
- admission creates Worker/Session/Task proof references, the initial fact and
  durable outbox before the lazy provider call can subscribe;
- proof loss quarantines and successful checkpoint logic cannot clear conflict;
- MySQL evidence is exact 8.0.44 and includes forward/reapply, Hibernate
  validate, target/generation/instance/proof/reference/outbox, rollback floor,
  and destroyed-target cleanup;
- no secret-shaped changed content or activation-default regression exists;
- the schema plan is candidate-bound, exhaustive, ordered and digest-sealed;
  fresh/reapply/validate is green; execution performs no directory scan,
  rollback/fixture admission, or Hibernate-generated DDL;
- closed provisioning used only existing production APIs, accepted only
  server-generated IDs, performed zero activation mutations/provider effects,
  purged short-lived bootstrap material, and left a stopped immutable target;
- the final manifest/seal binds the generated user/Worker/modelConfig grant and
  any manifest/schema/profile/identity drift is rejected.

## Later activation execution sequence (not authorized by this runbook)

These steps describe the future bounded run. They must not be performed during
implementation or independent signoff.

1. Reconfirm the new accepted signoff, exact sealed runId/target/generated
   tuple/model, maximum one model submission, profile paths, cost boundary and
   an owned cleanup window. Recompute candidate, schema-plan, seal and manifest
   identities; any mismatch invalidates the signoff.
2. Run `doctor` from outside the stopped sealed target root. It must report
   `ACTIVATION_TARGET_DOCTOR_READY`, `phase=preflight`, and
   `writesPerformed=0`. A fixture snapshot is never accepted here.
3. Only after the new exact execution authorization, render both target
   activation switches true. Restart only the already sealed exact Compose
   project using `mysql:8.0.44`; revalidate schema-plan/result identity and
   Hibernate `validate`. Then start only the copied candidate Navigator and
   dedicated repo-source Worker and atomically write their exact PID files.
4. Start `watch` from a cwd outside the target root. It must continuously prove
   exactly the Navigator and Worker PID-file processes, all three loopback
   listeners, one runId-labelled MySQL container with restart policy `no`, and
   zero unknown controllers. A subprocess whose parent chain reaches either
   exact PID-file-owned runtime is workload and is excluded from controller
   inventory; an independent, orphaned, re-parented or cyclic process under the
   target root remains unknown and fails closed. Its output path must equal the
   manifest path.
5. Use a control client that reads the target-owned control token without
   exposing it in argv or logs. Call registration, then proof acquire. Readiness
   must bind the manifest/controller digests, candidate, active generation,
   registered instance, DB-time lease, exact Worker identity/build/protocol/
   capabilities, authenticated lifecycle inventory, provider configuration,
   and receipt-enabled state.
6. Submit exactly one new synthetic Session/Task with the sealed manifest tuple
   using only the narrow runtime credential and static no-tool prompt. Do not
   retry. Capture only content-free IDs, hashes, disposition/status, counts,
   reason codes, and timestamps.
7. Stop new enrollment. Explicitly quarantine the proof or allow the planned
   loss check to do so. Verify Worker/Session/Task remain authority-quarantined
   and that a successful checkpoint cannot restore `READY/NONE`.
8. Run `cleanup-plan`; compare its manifest digest out of band. Only then may
   the execution owner run `cleanup --confirmation <exact-digest>`. Cleanup
   sends SIGTERM only to revalidated PID-file-owned processes and runs Compose
   down only for the exact project/file. It preserves the target root and
   evidence. Any revalidation failure stops cleanup for manual review.
9. Purge runtime, Worker, provider, activation-control and database credential
   files after the cleanup result is sealed. Preserve only content-free
   evidence, schema/manifest/seal digests and cleanup counts. If purge ownership
   cannot be revalidated, stop and report the retained credential paths without
   reading them.

## Stable stop reasons

The key fail-closed reasons include `LIFECYCLE_SERVER_ACTIVATION_AUTHORITY_REQUIRED`,
`LIFECYCLE_ACTIVATION_CONTROL_DISABLED`, `LIFECYCLE_ACTIVATION_ADMISSION_DISABLED`,
`LIFECYCLE_ACTIVATION_CONTROLLER_DRIFT`, `LIFECYCLE_ACTIVATION_DATABASE_MISMATCH`,
`LIFECYCLE_ACTIVATION_PROOF_NOT_ACTIVE`, `LIFECYCLE_ACTIVATION_WORKER_NOT_READY`,
`LIFECYCLE_ACTIVATION_WORKER_IDENTITY_MISMATCH`, and the harness
`ACTIVATION_TARGET_*` / `ACTIVATION_CONTROLLER_*` codes. Record codes, not raw
transport exceptions. Replanned bootstrap failures additionally use stable
`ACTIVATION_SCHEMA_PLAN_*`, `ACTIVATION_PROVISIONING_*`,
`ACTIVATION_TARGET_SEAL_*`, and `ACTIVATION_CREDENTIAL_PURGE_*` families;
unclassified raw HTTP/SQL/process exceptions are not evidence and must map to
one safe reason before signoff.

## Evidence and cleanup boundary

The activation target is disposable; the evidence is not. Preserve the
manifest, controller observations (including a loss observation), source/tree
digests, sanitized readiness, MySQL markers, provider-effect count, one
submission count, terminal status, quarantine counts, cleanup plan/result, and
all command exit files. Never preserve credentials, prompt body, or response.

No step in this runbook authorizes commit, push, tag, publish, release, deploy,
existing Worker restart/upgrade, production activation, or another canary.
