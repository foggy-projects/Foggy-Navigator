# Genshin Miliastra Development

为原神千星奇域相关开发任务选择合适的社区工具链，并输出可直接执行的实现方案、代码或文件处理步骤。

## 使用场景

当用户需要以下操作时使用：
- 设计或实现千星奇域玩法逻辑、节点图逻辑、交互脚本
- 在 Python、TypeScript、DSL、IR、GIA 文件格式之间选择开发路径
- 基于社区仓库搭建 AI 友好的开发工作流
- 分析、生成、转换、校验千星奇域相关工程文件
- 为 Claude、Codex 或其他 Agent 生成千星奇域开发提示词、Skill、任务拆解

## 执行流程

1. 先识别用户任务属于哪一类：玩法逻辑、节点图编辑、TypeScript 开发、文件格式处理、知识问答、工程搭建、调试排错。
2. 明确目标产物：脚本、节点图方案、导出文件、转换器、编辑器扩展、Skill、提示词、研究结论。
3. 在下列社区工具链中选主路线，只保留一条主路线，其他仓库仅作为补充参考：
   - `Ayaya_Miliastra_Editor`：面向 Python 工作流、节点图导出、校验与自动排版
   - `genshin-ts`：面向 TypeScript 开发、AI 友好编码、工程化脚本编写
   - `Genshin-Impact-Miliastra-Wonderland-Code-Node-Editor-Pack`：面向 DSL、IR、GIA 双向转换、编辑器能力
   - `Miliastra-toolbox`：面向知识问答、MCP/Skill API、规则查询
   - `genshin-miliastra-file-format`：面向底层文件格式、字段结构、格式研究
4. 如果用户没有指定技术路线，按决策规则自动选择，并明确说明选择理由。
5. 先给出最小可行实现路径，再给出可扩展路径；不要一开始堆完整平台方案。
6. 如果任务需要编码，直接生成目标语言的最小可运行骨架，并标注该骨架依赖的仓库或格式假设。
7. 如果任务需要研究或说明，输出“任务理解、推荐工具链、实施步骤、风险与未知项”四部分。
8. 如果任务涉及社区逆向格式、非官方 DSL 或导出链路，明确标记哪些结论来自社区项目推断，哪些是已在仓库中显式实现的能力。

## 输入要求

用户最好提供：
- 目标内容类型：玩法、机关、剧情交互、UI、地图规则、文件工具
- 希望使用的语言或工作流：Python、TypeScript、节点图、DSL、文件转换
- 目标产物：代码、Skill、编辑器插件、文件分析脚本、开发方案

如果用户未提供，则默认：
- 优先补齐任务类型与目标产物
- 未指定语言时，优先在 `TypeScript` 与 `Python` 两条路线中二选一
- 未指定仓库时，由本 Skill 自动选主路线

## 输出格式

默认按以下结构输出：

### 任务理解

- 一句话重述目标
- 明确本次采用的主路线

### 推荐工具链

- 主仓库：`{repo-name}`
- 补充参考：`{repo-name}` 可选，最多两个
- 选择理由：`{why}`

### 实施步骤

1. `{step-1}`
2. `{step-2}`
3. `{step-3}`

### 产物

- 如果是编码任务：直接给出代码、目录结构或补丁建议
- 如果是方案任务：给出模块拆分、接口、数据流、验证方式
- 如果是 Skill 任务：给出 `SKILL.md` 初稿，必要时附带 `reference.md` 建议

### 风险与未知项

- `{unknown-or-risk-1}`
- `{unknown-or-risk-2}`

## 约束条件

- 不要把社区项目包装成官方 SDK；所有能力默认视为社区工具链能力。
- 不要混用多条主路线导致实现路径失焦；必须明确主仓库。
- 不要凭空编造节点、DSL 语法、导出格式字段；无法确认时明确写“待查仓库实现”。
- 用户要求直接产出代码时，优先给最小闭环实现，不先输出冗长背景介绍。
- 用户要求创建 Skill 时，Skill 内容应面向 AI 执行，不写成人类教程文风。
- 涉及 GIA、IR、导出格式时，优先复用现有仓库已知结构，不重新发明文件协议。
- 涉及自动化、格式解析、逆向推断时，提醒用户这是社区资料链路，存在版本漂移风险。

## 决策规则

- 如果用户要“让 AI 直接写千星奇域逻辑”或“先快速做玩法原型” -> 优先使用 `genshin-ts`
- 如果用户要“从代码生成节点图”或“做 Python 驱动的节点编排” -> 优先使用 `Ayaya_Miliastra_Editor`
- 如果用户要“做 GIA/IR/DSL 转换器、编辑器、格式工具” -> 优先使用 `Genshin-Impact-Miliastra-Wonderland-Code-Node-Editor-Pack`
- 如果用户要“做问答助手、MCP、知识查询接口” -> 优先使用 `Miliastra-toolbox`
- 如果用户要“确认字段结构、研究底层文件格式” -> 优先使用 `genshin-miliastra-file-format`
- 如果用户只说“帮我做千星奇域项目”且信息不足 -> 先追问目标产物与首选语言；追问失败时默认走 `genshin-ts`
- 如果多个仓库都能做 -> 选择对当前目标产物最短路径的仓库，而不是功能最多的仓库
- 如果仓库能力与需求之间仍有缺口 -> 先说明缺口，再给出“基于现有仓库扩展”的实现方案

## 首选仓库映射

- `Ayaya_Miliastra_Editor`：代码到节点图、Python 驱动、校验、排版、导出
- `genshin-ts`：TypeScript 脚本化开发、AI 生成代码、工程化开发体验
- `Genshin-Impact-Miliastra-Wonderland-Code-Node-Editor-Pack`：GIA、IR、DSL、编辑器与转换链路
- `Miliastra-toolbox`：知识库、问答、MCP、Skill API
- `genshin-miliastra-file-format`：文件格式说明、底层结构研究

## 默认回答策略

- 简单问题：直接给出路线判断和下一步动作
- 技术选型问题：给结论优先级，不做泛泛横评
- 创建 Skill：优先输出可落地的 `SKILL.md` 初稿
- 创建代码：直接写最小可运行版本，并说明依赖仓库
- 研究型问题：区分“仓库已明确实现”和“根据仓库推断”
